# Нормализованная схема данных

Технические атрибуты `created_at` и `updated_at` не включены в атрибуты отношений
и функциональные зависимости, поскольку зависят от ключа строки и не
влияют на нормальную форму. Тем не менее ниже они указаны среди ограничений
каждого отношения: оба атрибута обязательны, получают текущее время при
создании строки, а `updated_at` обновляется триггером.
Все атрибуты моментов времени (`*_at`) имеют тип `timestamptz`; расчёт
календарных месяцев и лет для периодов выполняется в часовом поясе UTC,
а `day` означает ровно 24 часа.

Ограничения внутри таблицы закрепляются в DDL через `NOT NULL`, `CHECK` и
`UNIQUE`. Межтабличные ограничения проверяются триггерами БД. 
Для защиты от гонок данных (Race Conditions) используются транзакционные блокировки 
(`FOR UPDATE`) и рекомендательные блокировки (`pg_advisory_xact_lock`). 
Соблюдается принцип наименьших привилегий: структура БД и роли разделены, 
обычная роль приложения (`app_user`) не имеет прав на физическое удаление (`DELETE`) 
финансовых записей, а изменения структуры выполняет выделенная роль миграций.

## Домены перечислимых атрибутов

Имена ниже обозначают отдельные логические домены. В DDL каждый из них
закрепляется типом `ENUM` или ограничением `CHECK`; одинаковое имя атрибута
`status` в разных отношениях не означает общий набор значений.

| Домен | Атрибут | Допустимые значения |
| --- | --- | --- |
| `user_status` | `user.status` | `active`, `blocked`, `deleted` |
| `subscription_status` | `subscription.status` | `pending`, `active`, `paused`, `canceled`, `expired` |
| `payment_order_purpose` | `payment_order.purpose` | `subscription_period`, `donation` |
| `payment_order_origin` | `payment_order.origin` | `manual`, `auto_renewal` |
| `payment_order_status` | `payment_order.status` | `pending`, `processing`, `paid`, `failed`, `canceled` |
| `payment_attempt_status` | `payment_attempt.status` | `created`, `processing`, `succeeded`, `failed`, `canceled` |
| `refund_status` | `refund.status` | `pending`, `processing`, `succeeded`, `failed` |
| `refund_kind` | `refund.kind` | `customer_request`, `excess_charge` |
| `chargeback_status` | `chargeback.status` | `open`, `won`, `lost` |
| `post_status` | `post.status` | `draft`, `published`, `archived` |
| `billing_interval_unit` | `billing_plan.interval_unit` | `day`, `month`, `year` |
| `post_block_media_type` | `post_block.media_type` | `image`, `video`, `audio`, `file` |
| `notification_event_kind` | `notification.event_kind` | `post_published`, `comment_created`, `comment_liked`, `post_liked`, `subscription_changed`, `donation_received` |
| `currency_code` | `billing_plan.currency`, `payment_order.currency`, `payment_attempt.charged_currency` | трехбуквенные коды ISO 4217; актуальность проверяется при создании, исторические значения сохраняются |

## Отношения и функциональные зависимости

### Отношение `user`

Учетная запись пользователя.

`user(id, username, nickname, email, password_hash, avatar_key, status)`

#### Функциональные зависимости

```text
{id} -> username, nickname, email, password_hash, avatar_key, status
{username} -> id, nickname, email, password_hash, avatar_key, status
{email} -> id, username, nickname, password_hash, avatar_key, status
```

Первичный ключ — `{id}`. Потенциальные ключи — `{username}` и `{email}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется; `username` и
  `email` обязательны и имеют отдельные ограничения `UNIQUE`.
- `avatar_key` может быть `NULL`; остальные атрибуты обязательны.
- Значение по умолчанию `status` — `active`; значение должно принадлежать
  домену `user_status`. Для остальных атрибутов значения по умолчанию не задаются.
- Допустимые переходы `status`: `active → blocked/deleted`,
  `blocked → active/deleted`. Статус `deleted` конечный;
  переходы проверяются триггером при изменении строки.
- Физическое удаление пользователя запрещено при наличии зависимых профиля
  автора, подписок, платежных данных, комментариев или уведомлений. Удаление происходит только логически (Soft Delete)
  Лайки пользователя удаляются каскадно.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Все потенциальные ключи одноатрибутные, поэтому частичных
  зависимостей от составного ключа нет.
- **3НФ.** Неключевые атрибуты не зависят друг от друга.
- **НФБК.** Каждый детерминант (`id`, `username`, `email`) является
  потенциальным ключом.

### Отношение `author`

Профиль автора, являющийся необязательным расширением пользователя.

`author(id, bio, category, payout_provider, payout_account_id)`

#### Функциональные зависимости

```text
{id} -> bio, category, payout_provider, payout_account_id
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, неизменяем и одновременно является FK на `user.id`; такая
  схема обеспечивает связь профиля с пользователем 1:1.
- `category`, `payout_provider` и `payout_account_id` могут быть `NULL`; `bio`
  обязателен и по умолчанию содержит пустую строку.
  Для остальных атрибутов значения по умолчанию не задаются.
- `payout_provider` и `payout_account_id` либо заполнены вместе, либо оба равны
  `NULL`.
- Заполненная пара `{payout_provider, payout_account_id}` уникальна.
- Удаление пользователя с профилем автора запрещено. Автор с зависимыми
  уровнями подписки, пожертвованиями или публикациями также не удаляется
  физически, только логически.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Неключевые атрибуты не зависят друг от друга.
- **НФБК.** Единственный детерминант `id` является ключом.

### Отношение `subscription_type`

Уровень подписки, созданный конкретным автором.

`subscription_type(id, author_id, name, description, level, retired_at)`

#### Функциональные зависимости

```text
{id} -> author_id, name, description, level, retired_at
```

Первичный ключ — `{id}`. Пары `{author_id, name}` и `{author_id, level}`
уникальны только среди неархивных типов, поэтому не являются потенциальными
ключами всего отношения.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `author_id` обязателен и является FK на `author.id`; после создания строки
  не изменяется. Триггер отклоняет попытку его обновления, чтобы существующие
  планы, периоды подписки и правила доступа не меняли автора задним числом.
- Для неархивных типов (`retired_at IS NULL`) пары `{author_id, name}` и
  `{author_id, level}` закрепляются отдельными частичными уникальными
  индексами. После архивирования имя и номер уровня можно использовать для
  нового типа того же автора; старые строки сохраняются.
- `retired_at` может быть `NULL`; остальные атрибуты обязательны.
- Значения по умолчанию для атрибутов не задаются.
- `level` должен быть положительным.
- `level` не изменяется после создания строки: триггер отклоняет попытку его
  обновления. Поэтому ссылки на `subscription_type` сохраняют исторический
  уровень доступа; изменение уровня требует создания нового типа подписки.
- `name` и `description` служат описанием в каталоге и не участвуют в
  расчёте доступа или цены. Если описание содержит обещанные покупателю
  условия, их изменение требует нового типа: эта схема не хранит отдельные
  версии таких обещаний.
- Используемый уровень не удаляется физически: архивирование отмечается
  через `retired_at`. Физическое удаление уровня при наличии планов оплаты или правил
  доступа к публикациям запрещено. Архивирование необратимо: для повторного
  предложения создаётся новая строка.
- После архивирования типа запрещено создавать новые договоры и расчетные
  периоды по любому его плану, в том числе при автопродлении. При создании
  заказа на период проверяются `subscription_type.retired_at IS NULL` и
  `billing_plan.retired_at IS NULL`; уже созданные до архивирования заказы
  могут завершиться по прежним условиям. Архивирование не отзывает доступ
  по ранее оплаченным периодам.
- Типы одного автора с одинаковым `level`, созданные в разные периоды жизни
  каталога, имеют одинаковый ранг доступа. Пока старый оплаченный период
  действует, его владелец может читать посты с порогом нового типа того же
  ранга, и наоборот; это следует из сравнения числовых уровней.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Единственный потенциальный ключ одноатрибутный, поэтому
  частичных зависимостей нет.
- **3НФ.** Транзитивных зависимостей между неключевыми атрибутами нет.
- **НФБК.** Единственный безусловный детерминант `id` является ключом.

### Отношение `billing_plan`

Вариант оплаты уровня подписки: цена, валюта и периодичность.

`billing_plan(id, subscription_type_id, interval_unit, interval_count,
amount_minor, currency, retired_at)`

#### Функциональные зависимости

```text
{id} -> subscription_type_id, interval_unit, interval_count, amount_minor, currency, retired_at
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `subscription_type_id` обязателен и является FK на `subscription_type.id`;
  удаление уровня при наличии планов запрещено.
- `retired_at` может быть `NULL`; остальные атрибуты обязательны.
- Значения по умолчанию для атрибутов не задаются.
- `interval_unit` принимает значение из домена `billing_interval_unit`;
  `interval_count` и `amount_minor` должны быть положительными;
  `currency` принадлежит домену `currency_code`.
- Для действующих планов (`retired_at IS NULL`) набор
  `{subscription_type_id, interval_unit, interval_count, currency}` уникален.
- План, на который уже ссылаются договор или расчётный период, не удаляется.
  После первого использования неизменяемы `subscription_type_id`,
  `interval_unit`, `interval_count`, `amount_minor` и `currency`; изменение
  любого из них требует нового плана. Это проверяет триггер при обновлении
  плана. Архивирование отмечается `retired_at` и необратимо.
- Для нового заказа или продления недостаточно действующего плана: связанный
  `subscription_type` также не должен быть архивирован. Старые оплаченные
  периоды продолжают ссылаться на использованный план и тип.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Данные уровня подписки вынесены в отдельное отношение, на которое
  ссылается `subscription_type_id`; транзитивных зависимостей нет.
- **НФБК.** Единственный детерминант `id` является ключом.

### Отношение `subscription`

Договор пользователя с автором. `billing_plan_id` указывает выбранный план
для следующей покупки периода или автопродления, если оно включено.

`subscription(id, user_id, billing_plan_id, status, started_at,
cancellation_requested_at, ended_at)`

#### Функциональные зависимости

```text
{id} -> user_id, billing_plan_id, status, started_at, cancellation_requested_at, ended_at
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `user_id` и `billing_plan_id` обязательны и являются FK на `user.id` и
  `billing_plan.id` соответственно; удаление пользователя или плана при
  наличии договора запрещено. `user_id` и `started_at` после создания
  неизменяемы.
- Самоподписка запрещена: `subscription.user_id` не должен совпадать с
  `subscription_type.author_id` уровня выбранного `billing_plan_id`. Условие
  проверяется `BEFORE`-триггером при создании договора и смене плана.
- Смена `billing_plan_id` договора допускается только на план того же автора. 
  Попытка сменить план на уровень другого автора блокируется триггером.
- Договор создаётся при первом оформлении подписки с уже выбранным планом;
  поэтому `billing_plan_id` заполнен и при статусе `pending`. Договор, первый
  `payment_order` и его `subscription_period` создаются в одной транзакции;
  план первого периода равен выбранному плану договора.
- После изменения `subscription.billing_plan_id` новый план применяется к
  следующему заказу, который ещё не создан. Заказы и периоды, созданные
  раньше, сохраняют собственный `subscription_period.billing_plan_id`;
  смена плана на другой уровень того же автора допускается. Поэтому план
  договора не всегда равен плану последнего купленного периода.
- `cancellation_requested_at` может быть `NULL`. При его заполнении новые
  заказы автопродления не создаются, а уже созданные неоплаченные заказы
  с `origin = 'auto_renewal'` отменяются. Подтверждённое позднее списание
  по отменённому заказу сохраняется и возвращается как `excess_charge`.
  Договор остаётся `active` или `paused` до окончания уже оплаченного
  интервала; при `active` доступ сохраняется до его конца либо досрочного
  отзыва. Ручное возобновление до завершения договора очищает
  `cancellation_requested_at`; после конечного статуса нужен новый договор.
  `ended_at` заполнен тогда и
  только тогда, когда `status` равен `canceled` или `expired`; остальные
  атрибуты обязательны.
- Значение по умолчанию `status` — `pending`; значение должно принадлежать
  домену `subscription_status`. Для остальных атрибутов
  значения по умолчанию не задаются.
- Допустимые переходы `status`: `pending → active/canceled`,
  `active → paused/canceled/expired`, `paused → active/canceled/expired`.
  Статусы `canceled` и `expired` конечные; переходы проверяются триггером.
- Ограничение `CHECK ((status IN ('canceled', 'expired')) =
  (ended_at IS NOT NULL))` связывает `status` и `ended_at`; при заполненном
  `ended_at` требуется `ended_at >= started_at`. Переход в
  конечный статус и установка `ended_at` выполняются атомарно.
  При `expired` `cancellation_requested_at` равно `NULL`.
- Статус `active` описывает действующий договор, но сам по себе не дает
  доступа: требуется оплаченный и не отозванный период.
  Отсутствие такого периода не требует смены статуса
  договора.
- `paused` означает приостановку договора: платный доступ и автопродление
  прекращаются немедленно, но уже оплаченные периоды не удаляются и их
  границы не сдвигаются. Неоплаченные заказы с
  `origin = 'auto_renewal'` отменяются; позднее списание по ним возвращается.
  После `paused → active` доступ возвращается только при наличии ещё
  действующего оплаченного интервала.
- Если отмена запрошена, `canceled` и `ended_at` устанавливаются, когда
  закончился последний уже оплаченный интервал доступа; если такого интервала
  нет, отмена завершается сразу. До этого момента преждевременный переход
  `active/paused → canceled` запрещён.
- `expired` означает завершение договора после
  исчерпания попыток продления без запроса на отмену и после конца последнего
  оплаченного интервала; отсутствие доступа
  само по себе не переводит договор в `expired`.
- Для одной пары «пользователь — автор» допускается не более одного договора
  в незавершённом статусе `pending`, `active` или `paused`. Правило проверяется
  триггером. Для исключения состояния гонки перед проверкой 
  выполняется пессимистичная блокировка строки `user` подписчика (`SELECT ... FOR UPDATE`).
- Если текущий `billing_plan_id` договора указывает на архивный план или
  архивный тип, автопродление не создаёт новый заказ. До следующего периода
  можно выбрать действующий план того же автора; уже оплаченные периоды от
  такой смены не изменяются.
- Автопродление разрешено только при `status = 'active'`,
  `cancellation_requested_at IS NULL`, действующих плане и типе и отсутствии
  уже созданного заказа на то же продление.
- Если первый заказ закрыт без оплаты, то `pending → canceled`,
  а `ended_at` записывается в той же транзакции. При отмене по инициативе
  пользователя одновременно заполняется `cancellation_requested_at`.
- Договор с расчетными периодами или уведомлениями не удаляется физически;
  завершение отражается статусом и `ended_at`.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Данные плана оплаты вынесены в отдельное отношение, что исключает
  транзитивные зависимости.
- **НФБК.** Единственный детерминант `id` является ключом.

### Отношение `payment_order`

Платёжное обязательство за период подписки или пожертвование с ожидаемой
суммой, валютой и плательщиком.

`payment_order(id, payer_id, request_key, purpose, origin, expected_amount_minor,
currency, status, credited_attempt_id, expires_at, paid_at, canceled_at)`

#### Функциональные зависимости

```text
{id} -> payer_id, request_key, purpose, origin, expected_amount_minor, currency, status, credited_attempt_id, expires_at, paid_at, canceled_at
{request_key} -> id, payer_id, purpose, origin, expected_amount_minor, currency, status, credited_attempt_id, expires_at, paid_at, canceled_at
```

Первичный ключ — `{id}`. Потенциальный ключ — `{request_key}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `payer_id` обязателен и является FK на `user.id`; удаление плательщика при
  наличии платежных обязательств запрещено. `payer_id`, `purpose`, `origin`,
  `expected_amount_minor`, `currency`, `request_key` и `expires_at` после создания
  неизменяемы.
- `request_key` обязателен и глобально уникален. Повтор запроса на создание
  того же заказа возвращает существующий заказ с этим ключом; новая
  сознательная покупка использует новый ключ. Ключ продления детерминирован
  договором и номером продлеваемого периода. Повтор ключа с другим
  плательщиком, предметом, способом создания, суммой, валютой или сроком
  действия отклоняется.
  Сравниваются также поля дочернего `subscription_period` либо `donation`:
  ключ нельзя повторно использовать для другой подписки, плана или
  пожертвования.
- `credited_attempt_id`, `expires_at`, `paid_at` и `canceled_at` могут быть `NULL`; остальные
   атрибуты обязательны.
- Логика статусов строго связана с полями дат через эквивалентность. При `status = 'paid'`
  обязаны быть заполнены `paid_at` и `credited_attempt_id`, а при любом другом статусе 
  оба поля обязаны быть `NULL` (строгий `CHECK`). То же касается `status = 'canceled'` и `canceled_at`.
- `credited_attempt_id` использует составной внешний ключ (Composite FK) на `payment_attempt`.
  Ключ гарантирует, что попытка принадлежит именно этому заказу, имеет статус успешной 
  (т.к. суммы заполняются только при успехе), и что списанная сумма точно равна ожидаемой.
- После зачёта `credited_attempt_id` и `paid_at` не изменяются; после
  отмены `canceled_at` не изменяется.
- Значение по умолчанию `status` — `pending`; `status` и `purpose` принимают только
  значения из доменов `payment_order_status` и `payment_order_purpose`
  соответственно. `origin` принимает значения из `payment_order_origin`;
  пожертвование и первый заказ нового договора всегда имеют
  `origin = 'manual'`. Для остальных атрибутов значения по умолчанию не
  задаются.
- Допустимые переходы `status`: `pending → processing/paid/failed/canceled`,
  `processing → paid/failed/canceled`, `failed → processing/paid/canceled`.
  `paid` и `canceled` — конечные состояния платежного обязательства; повторная попытка
  после неудачи создает новую строку `payment_attempt`, а переходы статуса
  заказа проверяются триггером. Возврат денег не переписывает факт `paid`.
- `expected_amount_minor` должен быть положительным, а `currency` должна
  принадлежать домену `currency_code`.
- Обязательство получает статус `paid` только после
  успешного закрепления одной попытки и, для подписки, окончательного начала
  периода. `paid_at` фиксирует момент зачёта в БД; попытку, по которой уже
  создан возврат или проигран спор, зачесть нельзя. Реальное списание по уже
  `paid` или `canceled` заказу всё равно
  сохраняется как успешная попытка без повторной выдачи доступа.
- Если заказ имеет `expires_at` и оплата не зачтена к этому моменту,
  заказ переводится в `canceled`; подтверждённое позже списание возвращается.
- Межтабличное XOR-правило: каждый заказ связан ровно с одной строкой `subscription_period` 
  или `donation` (в зависимости от `purpose`). Это проверяется отложенным триггером 
  (`DEFERRABLE INITIALLY DEFERRED`). База проверяет счетчики дочерних строк только 
  в момент `COMMIT` транзакции, что исключает гонки при конкурентном создании.
- `payment_order` и строка его назначения создаются в одной транзакции:
  вместе с `subscription_period` при оплате периода либо вместе с `donation`
  при пожертвовании. До `COMMIT` заказ может временно не иметь дочерней строки,
  но после успешной транзакции не может остаться без нее.
- Зачёт одной успешной попытки и перевод заказа в `paid` выполняются одной
  транзакцией. Сохранение факта успешного списания не зависит от возможности
  зачесть его: лишнюю или несвоевременную успешную попытку сохраняют,
  а затем создают полный возврат с `kind = 'excess_charge'`.
- Платежное обязательство и зависимые финансовые данные физически не удаляются, только
  логически через статус.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Попытки оплаты и данные пользователя вынесены в отдельные отношения,
  транзитивных зависимостей нет.
- **НФБК.** Оба детерминанта (`id` и `request_key`) являются ключами.

### Отношение `subscription_period`

Покупка расчётного периода подписки и план, выбранный для её оплаты. Строка создаётся
до подтверждения платежа и сама по себе не даёт доступа. До зачёта оплаты
начало периода предварительное; после зачёта оно становится окончательным.

`subscription_period(payment_order_id, subscription_id, billing_plan_id,
period_start, revoked_at)`

#### Функциональные зависимости

```text
{payment_order_id} -> subscription_id, billing_plan_id, period_start, revoked_at
```

Первичный ключ — `{payment_order_id}`.

#### Ограничения целостности и бизнес-правила

- `payment_order_id` обязателен, неизменяем и одновременно является FK на
  `payment_order.id`; этим обеспечивается связь платежного обязательства с
  периодом 1:0..1.
- `subscription_id` и `billing_plan_id` обязательны и являются FK на
  `subscription.id` и `billing_plan.id` соответственно. `revoked_at` может быть
  `NULL`; остальные атрибуты обязательны. `subscription_id` и
  `billing_plan_id` после создания неизменяемы.
- При создании заказа на период его `billing_plan_id` равен
  `subscription.billing_plan_id` в момент создания, причем это выполняется в транзакции создания
  заказа и периода; последующая смена плана договора не меняет уже созданный
  период.
- Тариф периода должен принадлежать тому же автору, что и текущий тариф
  связанной подписки: авторы уровней, на которые ссылаются
  `subscription_period.billing_plan_id` и `subscription.billing_plan_id`,
  должны совпадать. Правило проверяется триггером
  при создании периода и при смене текущего тарифа подписки.
- Значения по умолчанию для атрибутов не задаются.
- Несколько неоплаченных заказов одной подписки могут иметь одинаковое
  предварительное начало периода. Это не выдаёт доступ и не резервирует оплаченный
  интервал; повторная покупка после окончательной отмены заказа возможна.
- Новый период создаётся только по неархивным `billing_plan` и
  `subscription_type`. Архивирование после создания заказа и периода не
  отменяет уже начатую оплату; новые заказы по ним не создаются. Транзакция
  создания заказа блокирует строки плана и типа до `COMMIT`, чтобы проверка
  архивации и первая фиксация условий не расходились с параллельным
  редактированием или архивированием.
- Окончание периода (`period_end`) не хранится в БД, чтобы не создавать функциональную 
  зависимость, нарушающую НФБК (т.к. дата зависела бы от тарифа и старта). Дата 
  вычисляется `IMMUTABLE`-функцией в UTC на основе `interval_unit` и `interval_count`. 
  Для удобства приложения создано представление (View) `subscription_period_with_end`.
- Оплаченные интервалы доступа одной подписки не пересекаются.
- `billing_plan_id` фиксирует план и его коммерческие условия на момент
  создания заказа;
  после использования они не изменяются. `subscription_id` не определяет
  `billing_plan_id` периода: текущий план договора может измениться между
  периодами, а старые периоды продолжают ссылаться на прежний план.
- `revoked_at` фиксирует момент досрочного отзыва доступа к этому периоду;
  `NULL` означает, что доступ досрочно не отзывался. Для текущего момента времени `t` период
  даёт доступ только при `period_start <= t`, пока `t` меньше вычисленного
  окончания периода, и при (`revoked_at IS NULL` или `t < revoked_at`),
  если связанный заказ имеет
  статус `paid`, а договор — `active`. Уровень и автор для проверки доступа
  берутся из `subscription_period.billing_plan_id` через `subscription_type`;
  порог публикации берётся из `post_access`. Изменение `revoked_at` допускает
  только триггер подтверждённого возврата или проигранного спора.
- Если полный возврат зачтённой попытки завершён до окончания периода,
  `revoked_at` устанавливается в `refund.completed_at` в той же транзакции.
  То же правило действует при подтверждённом проигранном споре о списании:
  используется `chargeback.resolved_at`. Если оба события произошли,
  сохраняется более ранний момент отзыва. После окончания периода доступ уже истёк,
  поэтому позднее событие не заполняет `revoked_at`. Возврат или спор по
  незачтённой попытке не меняет период.
- При создании периода `payment_order.expected_amount_minor` и
  `payment_order.currency` должны совпадать с `billing_plan.amount_minor` и
  `billing_plan.currency` его зафиксированного плана. Проверка выполняется
  атомарно с созданием связанных платежного обязательства и периода.
- `payment_order.payer_id` должен совпадать с `subscription.user_id`;
  совпадение проверяется триггером. Соответствие `purpose` дочернему
  отношению обеспечивает общее XOR-правило заказа.
- Физическое удаление связанного платежного обязательства, договора или плана запрещено;
  расчетный период как финансовая запись физически не удаляется.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, частичных зависимостей нет.
- **3НФ.** Неключевые атрибуты зависят от ключа; транзитивных зависимостей нет.
- **НФБК.** Единственный детерминант является ключом. Строгое соответствие НФБК достигается благодаря тому, что вычисляемое поле `period_end` не хранится в таблице физически, а вычисляется "на лету" через представление `subscription_period_with_end`.

### Отношение `payment_attempt`

Отдельная попытка провести платеж через внешнего провайдера.

`payment_attempt(id, payment_order_id, provider, external_transaction_id,
status, charged_amount_minor, charged_currency,
failure_reason, completed_at)`

#### Функциональные зависимости

```text
{id} -> payment_order_id, provider, external_transaction_id, status, charged_amount_minor, charged_currency, failure_reason, completed_at
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `payment_order_id` обязателен и является FK на `payment_order.id`; удаление
  платежного обязательства при наличии попыток запрещено. `payment_order_id`
  и `provider` после создания неизменяемы.
- `id` генерируется и строка попытки со статусом `created` сохраняется до обращения 
  к провайдеру. **Приложение строго разделяет локальные транзакции БД и внешние сетевые вызовы**. 
  Протокол приложения:
  1. Транзакция БД 1: создание строки `payment_attempt` (`COMMIT`).
  2. Вне транзакции БД: HTTP-запрос к провайдеру, где `payment_attempt.id` передаётся 
     как ключ идемпотентности.
  3. Транзакция БД 2: получение ответа и обновление статуса попытки на `processing`, 
     `succeeded` или `failed` (`COMMIT`). 
  Это исключает удержание длительных блокировок БД во время ожидания ответа по сети.
- `external_transaction_id`, `charged_amount_minor`, `charged_currency`,
  `failure_reason` и `completed_at` могут быть
  `NULL`; остальные атрибуты обязательны.
- Значение по умолчанию `status` — `created`; значение должно принадлежать
  домену `payment_attempt_status`. Для остальных
  атрибутов значения по умолчанию не задаются.
- Допустимые переходы `status`: `created → processing/succeeded/failed/canceled`,
  `processing → succeeded/failed/canceled`. Полученное позже подтверждение
  реального списания переводит также `failed` или `canceled` в `succeeded`;
  `succeeded` — конечное состояние.
- Заполненная пара `{provider, external_transaction_id}` уникальна, но не
  является потенциальным ключом, поскольку `external_transaction_id` может
  быть `NULL`. Пара `{payment_order_id, external_transaction_id}` отдельно
  не уникальна: идентификаторы разных провайдеров могут совпадать.
- У успешной попытки обязательны `external_transaction_id`,
  `charged_amount_minor`, `charged_currency` и `completed_at`;
  `charged_amount_minor > 0`. Эти поля фиксируют фактическое списание и
  после успеха не изменяются; валюта принадлежит `currency_code`.
  До успеха сумма и валюта фактического
  списания равны `NULL`. У `failed` и `canceled` обязательна
  `failure_reason`, которая очищается при позднем подтверждении успеха;
  у `created`, `processing` и `succeeded` она равна `NULL`.
- У одного заказа могут быть несколько разных успешных попыток. Повторное
  сообщение об одной транзакции обновляет ту же попытку и не создаёт нового
  списания; две разные внешние транзакции сохраняются отдельно. Лишь попытка
  из `payment_order.credited_attempt_id` оплачивает заказ. Остальные
  успешные попытки подлежат полному возврату.
- Попытка оплаты является финансовой записью и физически не удаляется.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Каждая попытка представлена отдельной строкой, все значения атомарны.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Неключевые атрибуты не зависят друг от друга.
- **НФБК.** Единственный безусловный детерминант `id` является ключом.

### Отношение `provider_webhook_event`

Учёт полученных событий провайдера для идемпотентной обработки вебхуков.

`provider_webhook_event(provider, external_event_id, event_kind, processed_at)`

#### Функциональные зависимости

```text
{provider, external_event_id} -> event_kind, processed_at
```

Первичный ключ — `{provider, external_event_id}`.

#### Ограничения целостности и бизнес-правила

- Все атрибуты, кроме `processed_at`, обязательны. `created_at` задаётся
  сервером при первом получении события. `event_kind` — непустое имя события
  внешнего провайдера, не домен `notification.event_kind`. Пара ключевых
  атрибутов и `event_kind` после создания не изменяются; заполненный
  `processed_at` не очищается и не меняется.
- Повтор события с теми же `{provider, external_event_id}` не создаёт новую
  строку и не повторяет финансовое изменение. Пока `processed_at IS NULL`,
  обработку можно возобновить. Применение события к попытке оплаты, возврату
  или спору и установка `processed_at` происходят одной транзакцией.
- Запись события не удаляется физически. `created_at` и `updated_at`
  обязательны, по умолчанию равны текущему времени; `updated_at`
  поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны.
- **2НФ.** Неключевые атрибуты зависят от всей пары ключа.
- **3НФ и НФБК.** Единственный детерминант является ключом.

### Отношение `refund`

Запрос и результат полного возврата одного подтверждённого списания. Это может быть
зачтённый платёж по заказу или лишнее списание.

`refund(id, payment_attempt_id, external_refund_id, amount_minor, kind,
reason, status, completed_at)`

#### Функциональные зависимости

```text
{id} -> payment_attempt_id, external_refund_id, amount_minor, kind, reason, status, completed_at
{payment_attempt_id} -> id, external_refund_id, amount_minor, kind, reason, status, completed_at
```

Первичный ключ — `{id}`. Потенциальный ключ — `{payment_attempt_id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `payment_attempt_id` обязателен и является FK на успешную
  `payment_attempt.id`. После создания ссылка не изменяется. Попытка и
  связанный заказ физически не удаляются.
- `payment_attempt_id` уникален: одно фактическое списание допускает не более
  одного полного возврата, включая незавершённый или неудачный. Разные
  успешные попытки одного заказа могут иметь отдельные возвраты.
- `id` генерируется и запись сохраняется до обращения к провайдеру.
  Ключ `refund.id` служит ключом идемпотентности полного возврата; повтор
  запроса использует тот же ключ.
- `kind = 'customer_request'` допускается только для попытки, указанной
  в `payment_order.credited_attempt_id` оплаченного заказа. Для незачтённой
  успешной попытки используется `kind = 'excess_charge'`.
- После подтверждённого `chargeback.status = 'lost'` новый возврат по тому
  же списанию не инициируется.
- Запрос пользователя на возврат можно зарегистрировать и после окончания
  оплаченного периода. Предельный срок задаётся отдельной политикой
  приложения: для
  подписки он отсчитывается от вычисленного окончания периода, для
  пожертвования — от `payment_order.paid_at`. Политика проверяет дату подачи
  запроса (`refund.created_at`). На автоматический возврат лишнего списания
  этот срок не распространяется.
- `external_refund_id` и `completed_at` могут быть `NULL`; остальные атрибуты
  обязательны. `amount_minor` и `reason` не имеют значения по умолчанию;
  `kind` принадлежит домену `refund_kind`. `amount_minor`, `kind` и `reason`
  после создания не изменяются, `external_refund_id` и `completed_at`
  после успешного возврата не изменяются.
- Значение по умолчанию `status` — `pending`; допустимые переходы:
  `pending → processing/succeeded/failed`, `processing → succeeded/failed`,
  `failed → processing/succeeded`. Позднее подтверждение фактического возврата
  требует `failed → succeeded`; `succeeded` — конечный статус. Переходы
  проверяются триггером. Повтор сетевого запроса использует ту же запись
  и тот же ключ идемпотентности; `failed → processing` разрешён только при
  повторной обработке той же операции провайдера. Окончательный отказ
  провайдера, после которого этот ключ уже нельзя повторить, требует
  ручного урегулирования.
- `amount_minor` положителен и точно равен фактической
  `payment_attempt.charged_amount_minor`: частичные возвраты не реализуются.
  Это равенство строго обеспечивается на уровне БД с помощью составного внешнего ключа (Composite FK) `fk_refund_attempt_amount`, который ссылается на пару `(id, charged_amount_minor)` в таблице `payment_attempt`. Валюта возврата равна `payment_attempt.charged_currency`.
- У успешного возврата обязательны `external_refund_id` и `completed_at`.
  `completed_at` фиксирует момент регистрации подтверждения в БД, чтобы
  отзыв доступа не устанавливался задним числом. При остальных статусах
  `completed_at` равен `NULL`.
- Идентификатор `external_refund_id` уникален в рамках провайдера. Поскольку 
  провайдер хранится в другой таблице (`payment_attempt`), уникальность обеспечивается 
  рекомендательной блокировкой `pg_advisory_xact_lock` по хэшу провайдера и ID. 
  Это исключает дубликаты при конкурентной обработке одинаковых вебхуков (Race Condition).
- Только успешный возврат зачтённой попытки по периоду может установить
  `subscription_period.revoked_at`, согласно правилу периода. Возврат
  пожертвования или лишнего списания не меняет периоды. Возврат сам по себе
  не меняет статус договора.
- Возврат является финансовой записью и физически не удаляется.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Все потенциальные ключи одноатрибутные, частичных зависимостей нет.
- **3НФ.** Транзитивных зависимостей нет.
- **НФБК.** Оба детерминанта (`id` и `payment_attempt_id`) являются
  потенциальными ключами.

### Отношение `chargeback`

Спор о подтверждённом списании, открытый у провайдера. Спор не является
добровольным возвратом `refund`.

`chargeback(id, payment_attempt_id, external_dispute_id, status, opened_at,
resolved_at)`

#### Функциональные зависимости

```text
{id} -> payment_attempt_id, external_dispute_id, status, opened_at, resolved_at
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
  `payment_attempt_id` обязателен и является FK на успешную
  `payment_attempt.id`; после создания ссылка не изменяется. Попытка и
  связанный заказ не удаляются.
- `external_dispute_id`, `status` и `opened_at` обязательны;
  `resolved_at` может быть `NULL`. `external_dispute_id` и `opened_at` после
  создания не изменяются.
- Пара из провайдера соответствующей попытки и `external_dispute_id` уникальна. 
  Как и в случае с возвратами, правило строго дедуплицируется триггером с 
  использованием `pg_advisory_xact_lock`, что блокирует параллельные вебхуки 
  об одном и том же споре на уровне БД.
- Значение `status` по умолчанию — `open`. Допустимые переходы:
  `open → won/lost`; `won` и `lost` конечные. `resolved_at` заполнен тогда и
  только тогда, когда спор решён; он фиксирует момент обработки окончательного
  решения в БД и не предшествует `opened_at`.
- Открытый спор не меняет доступ. Только окончательный `lost` по попытке,
  зачтённой за период подписки, досрочно отзывает его с `resolved_at`, если
  решение обработано до окончания периода. После окончания периода `revoked_at`
  остаётся `NULL`, если более раннего отзыва не было. Спор `won`, спор по
  незачтённой попытке и спор о пожертвовании не меняют периоды.
- Если по той же попытке есть добровольный возврат, оба финансовых события
  сохраняются; их денежные последствия требуют сверки с провайдером.
  `payment_order.status = 'paid'` сохраняет факт зачёта даже при `lost`.
- Спор сам по себе не меняет статус договора; он отзывает доступ только по затронутому периоду.
- Спор физически не удаляется. `created_at` и `updated_at` обязательны и по
  умолчанию равны текущему времени; `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны.
- **2НФ.** Ключ одноатрибутный, частичных зависимостей нет.
- **3НФ и НФБК.** Единственный безусловный детерминант `id` является ключом.

- **3НФ.** Данные о транзакции вынесены в отдельное отношение, поэтому

### Отношение `post`

Публикация автора

`post(id, author_id, title, body, status, published_at)`

#### Функциональные зависимости

```text
{id} -> author_id, title, body, status, published_at
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `author_id` обязателен и является FK на `author.id`; физическое удаление автора при
  наличии публикаций запрещено. После создания `author_id` не изменяется:
  иначе автор правила `post_access` мог бы перестать совпадать с автором
  публикации.
- `published_at` может быть `NULL`; остальные атрибуты обязательны.
- Значение по умолчанию `status` — `draft`; значение должно принадлежать
  домену `post_status`. Значение по умолчанию `body` — пустая
  строка. Для остальных атрибутов значения по умолчанию не задаются.
- Допустимые переходы `status`: `draft → published`, `published → archived`,
  `archived → published`. При повторной публикации `published_at` сохраняет
  время первой публикации; переходы проверяются триггером.
- При `status = 'published'` атрибут `published_at` обязателен, `title` после
  удаления пробельных символов не пуст, а содержимое представлено либо
  непустым `body`, либо хотя бы одним `post_block`.
  Публикация пустого поста запрещена; это условие проверяется
  также при изменении текста или удалении медиаблока. Проверка
  наличия блока требует транзакции приложения или триггера.
- Если создается платная публикация, `post` и соответствующий `post_access`
  создаются в одной транзакции; при публикации уже существующего черновика
  установка платного доступа и переход в `published` тоже атомарны. До
  завершения транзакции публикация не должна становиться видимой читателям.
  В текущей схеме признак платности определяется наличием `post_access`.
- При удалении публикации каскадно удаляются ее правило доступа, медиаблоки,
  лайки, комментарии и уведомления, для которых публикация является
  источником.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Данные автора и медиаблоки не дублируются; транзитивных зависимостей
  нет.
- **НФБК.** Единственный детерминант `id` является ключом.

### Отношение `post_access`

Минимальный уровень подписки для доступа к публикации, то есть доступ осуществляется
к указанному уровню и всем более высоким только внутри одного автора. Если строка отсутствует,
публикация общедоступна.

`post_access(post_id, subscription_type_id)`

#### Функциональные зависимости

```text
{post_id} -> subscription_type_id
```

Первичный ключ — `{post_id}`.

#### Ограничения целостности и бизнес-правила

- `post_id` обязателен, неизменяем и одновременно является FK на `post.id`;
  этим обеспечивается не более одного правила доступа для публикации.
- `subscription_type_id` обязателен и является FK на `subscription_type.id`.
- Значения по умолчанию для атрибутов не задаются.
- Уровень доступа должен принадлежать автору публикации. Триггер проверяет
  это при создании и смене `post_access.subscription_type_id`; автор поста
  и автор уровня после создания неизменяемы.
- Доступ определяется сравнением числовых `level` в рамках одного автора.
- Правило доступа удаляется каскадно вместе с публикацией; удаление используемого
  уровня подписки запрещено.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Оба атрибута атомарны
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Сведения об уровне подписки не дублируются; транзитивных зависимостей
  нет.
- **НФБК.** Единственный детерминант `post_id` является ключом.

### Отношение `post_block`

Медиаблок внутри публикации. В БД хранится ключ объекта, а не файл или URL.

`post_block(id, post_id, position, media_type, media_key, size_bytes)`

#### Функциональные зависимости

```text
{id} -> post_id, position, media_type, media_key, size_bytes
{post_id, position} -> id, media_type, media_key, size_bytes
{media_key} -> id, post_id, position, media_type, size_bytes
```

Первичный ключ — `{id}`. Потенциальные ключи —
`{post_id, position}` и `{media_key}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `post_id` обязателен и является FK на `post.id`.
- Все атрибуты обязательны; пары `{post_id, position}` и значения
  `media_key` уникальны.
- Значения по умолчанию для атрибутов не задаются.
- `position` и `size_bytes` должны быть неотрицательными.
- `media_type` принимает значение из домена `post_block_media_type`.
- Медиаблок удаляется каскадно вместе с публикацией.
- Удаление или перенос последнего медиаблока опубликованного поста с пустым `body` запрещены.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ни один неключевой атрибут не зависит только от `post_id` или только
  от `position`.
- **3НФ.** Сведения о посте вынесены в отдельное отношение; транзитивных зависимостей нет
- **НФБК.** Каждый детерминант является потенциальным ключом.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны
- **2НФ.** Неключевых атрибутов нет, поэтому частичных зависимостей нет.
- **3НФ.** Неключевых атрибутов нет, поэтому транзитивных зависимостей нет.
- **НФБК.** Оба детерминанта являются потенциальными ключами.

### Отношение `notification`

Уведомление пользователя. **Ровно одна** ссылка на источник должна быть заполнена.

`notification(id, user_id, event_kind, post_id, comment_id, comment_like_id,
post_like_id, subscription_id, donation_id, scheduled_at, sent_at, read_at)`

#### Функциональные зависимости

```text
{id} -> user_id, event_kind, post_id, comment_id, comment_like_id, post_like_id, subscription_id, donation_id, scheduled_at, sent_at, read_at
```

Первичный ключ — `{id}`.

#### Ограничения целостности и бизнес-правила

- `id` обязателен, генерируется автоматически и не изменяется.
- `user_id` обязателен и является FK на `user.id`;
- `post_id`, `comment_id`, `comment_like_id`, `post_like_id` и `subscription_id`
  являются FK на одноименные отношения. Ровно один из этих пяти атрибутов
  должен быть заполнен, остальные четыре должны быть `NULL`.
- `sent_at` и `read_at` могут быть `NULL`; `event_kind` и `scheduled_at`
  обязательны.
- Значения по умолчанию для атрибутов не задаются.
- `event_kind` принимает значение из домена `notification_event_kind`.
  Каждому значению соответствует определенный источник: `post_published` —
  `post_id`, `comment_created` — `comment_id`, `comment_liked` —
  `comment_like_id`, `post_liked` — `post_like_id`, `subscription_changed` —
  `subscription_id`.
- В PostgreSQL правило «ровно один источник, соответствующий виду события»
  закрепляется ограничением:

  ```sql
  ALTER TABLE notification
  ADD CONSTRAINT notification_source_kind_check CHECK (
      num_nonnulls(post_id, comment_id, comment_like_id,
                   post_like_id, subscription_id, donation_id) = 1
      AND (
          (event_kind = 'post_published' AND post_id IS NOT NULL)
          OR (event_kind = 'comment_created' AND comment_id IS NOT NULL)
          OR (event_kind = 'comment_liked' AND comment_like_id IS NOT NULL)
          OR (event_kind = 'post_liked' AND post_like_id IS NOT NULL)
          OR (event_kind = 'subscription_changed' AND subscription_id IS NOT NULL)
          OR (event_kind = 'donation_received' AND donation_id IS NOT NULL)
      )
  );
  ```
- `read_at` может быть заполнен только при заполненном `sent_at` и не может
  предшествовать `sent_at`.
- Уведомление удаляется каскадно при удалении своего источника. Для источника
  `subscription` физическое удаление запрещено, поэтому его уведомления
  сохраняются вместе с договором. При логическом удалении пользователя удалить
  неотправленные уведомления.
- `created_at` и `updated_at` обязательны и по умолчанию равны текущему времени;
  `updated_at` поддерживается триггером.

#### Нормальные формы

- **1НФ.** Все атрибуты атомарны: кортеж содержит одно значение для каждого
  атрибута.
- **2НФ.** Ключ одноатрибутный, поэтому частичных зависимостей нет.
- **3НФ.** Данные источников уведомления не копируются; транзитивных зависимостей
  нет.
- **НФБК.** Единственный детерминант `id` является ключом.

## Примеры транзакций приложения (Защита от состояния гонки)

Для обеспечения консистентности финансовых операций и недопущения выдачи дублирующего доступа бизнес-логика приложения использует транзакции с явными пессимистичными блокировками уровня строк (`FOR NO KEY UPDATE`).

### Сценарий 1: Две конкурентные успешные попытки дают не более одного зачёта
Если провайдер присылает вебхук об успешном списании (или дубль вебхука), транзакция гарантирует обработку строго один раз и защищает заказ от двойного зачёта. Лишнее списание не меняет статус заказа, оставляя возможность для возврата (`excess_charge`).

```sql
BEGIN;

INSERT INTO provider_webhook_event (provider, external_event_id, event_kind, processed_at)
VALUES ('stripe', 'evt_999', 'payment_intent.succeeded', now())
ON CONFLICT (provider, external_event_id) DO NOTHING;

-- Логика приложения: если affected_rows == 0, значит вебхук уже обработан, прерываем транзакцию (COMMIT и ответ 200 OK)

-- Сохраняем/обновляем статус попытки
INSERT INTO payment_attempt (id, payment_order_id, provider, external_transaction_id, status, charged_amount_minor, charged_currency)
VALUES ($1, $2, 'stripe', 'txn_123', 'succeeded', 500, 'USD')
ON CONFLICT (provider, external_transaction_id) 
DO UPDATE SET 
    status = EXCLUDED.status,
    charged_amount_minor = EXCLUDED.charged_amount_minor,
    charged_currency = EXCLUDED.charged_currency,
    completed_at = now()
WHERE payment_attempt.status NOT IN ('succeeded', 'failed', 'canceled'); -- защита от отката статуса

SELECT status FROM payment_order WHERE id = $2 FOR NO KEY UPDATE;

-- Логика приложения: если статус = 'pending' или 'processing', то зачитываем
UPDATE payment_order 
SET status = 'paid', paid_at = now(), credited_attempt_id = $1
WHERE id = $2 AND status IN ('pending', 'processing');

COMMIT;
```

### Сценарий 2: Два конкурентных продления не создают пересекающиеся оплаченные интервалы
При срабатывании крона автопродления на нескольких инстансах одновременно, необходимо гарантировать, что для одной подписки будет создан только один заказ на следующий период. Блокируется сама подписка.

```sql
BEGIN;

-- Блокируем подписку от конкурентных изменений
SELECT status, cancellation_requested_at, billing_plan_id
FROM subscription
WHERE id = $1
FOR NO KEY UPDATE;

-- Проверяем тариф и автора
SELECT bp.retired_at, st.retired_at 
FROM billing_plan bp
JOIN subscription_type st ON st.id = bp.subscription_type_id
WHERE bp.id = $2
FOR SHARE; -- запрет обновления тарифа

-- Логика приложения: Если status == 'active', cancellation_requested_at == NULL, и оба retired_at == NULL. Если нет - ROLLBACK

-- Проверяем наличие уже формирующегося заказа
SELECT 1 FROM payment_order po
JOIN subscription_period sp ON sp.payment_order_id = po.id
WHERE sp.subscription_id = $1 AND po.status IN ('pending', 'processing');

-- Логика приложения: если заказ найден -> ROLLBACK

-- Вычисляем старт для нового периода
SELECT period_end 
FROM subscription_period_with_end
WHERE subscription_id = $1
  AND po.status = 'paid' -- только оплаченные
  AND spe.revoked_at IS NULL -- только не отозванные
ORDER BY period_end DESC
LIMIT 1;

-- Логика приложения: Сохраняем полученный period_end в переменную $new_start. Если периодов нет, берем now().

INSERT INTO payment_order (id, payer_id, request_key, purpose, origin, expected_amount_minor, currency)
VALUES ($2, $3, $4, 'subscription_period', 'auto_renewal', $5, $6);

INSERT INTO subscription_period (payment_order_id, subscription_id, billing_plan_id, period_start)
VALUES ($2, $1, $7, $new_start);

COMMIT;
```

### Сценарий 3: Подтверждённый возврат зачтённого платежа отзывает доступ в той же транзакции
Операция гарантирует, что как только возврат отмечается в БД как успешный, доступ по периоду немедленно прекращается (атомарно).

```sql
BEGIN;

INSERT INTO provider_webhook_event (provider, external_event_id, event_kind, processed_at)
VALUES ('stripe', 'evt_refund_888', 'charge.refunded', now());

-- Обновляем статус возврата и возвращаем ID связанной попытки
UPDATE refund 
SET status = 'succeeded', completed_at = now(), external_refund_id = 're_123'
WHERE id = $1 
RETURNING payment_attempt_id;

-- Ищем заказ, оплаченный именно этой попыткой, и блокируем его период
SELECT sp.payment_order_id 
FROM subscription_period sp
JOIN payment_order po ON po.id = sp.payment_order_id
WHERE po.credited_attempt_id = $3 -- $3 получено из RETURNING ранее
FOR NO KEY UPDATE OF sp;

-- Если заказ найден, отзываем период подписки
UPDATE subscription_period 
SET revoked_at = now() 
WHERE payment_order_id = $4; -- $4 получено из предыдущего шага

COMMIT;
```

## Внешние сервисы и WebSockets

- **Redis** хранит временный кэш id опубликованных постов для ленты
  и счётчиков лайков.
- **MinIO** хранит аватары и файлы медиаблоков. В PostgreSQL остаются только
  ключи объектов (`user.avatar_key`, `post_block.media_key`) и метаданные;
  медиа платных постов выдаются через сервер после проверки права доступа.
- **WebSockets**. Поскольку в текущей архитектуре приложения не предусмотрены личные сообщения (чаты), функционал WebSockets будет реализован на базе сущностей **Уведомлений (`notification`)** и **Комментариев (`comment`)**.
